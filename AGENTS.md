# NEXORA — AGENTS.md

## 1. Project Identity

NEXORA is a retrofit-first Building Intelligence platform for smart buildings.

Core system loop:

SENSE → UNDERSTAND → PREDICT → DECIDE → GATE → ACT → VERIFY → LEARN

NEXORA does not replace the building or its existing BMS.

It acts as an intelligence and verification layer over existing building infrastructure.

Core prototype capabilities:

- Building and zone monitoring
- Occupancy awareness and prediction
- Energy monitoring
- Energy baseline and anomaly detection
- HVAC optimisation
- Lighting optimisation
- Comfort and IAQ monitoring
- AI recommendations
- Digital-twin / what-if evaluation
- Safety and constraint gating
- Human approval and manual override
- Simulated control actions
- Measurement and verification
- Facility-manager dashboard

The product should feel like a serious professional building-intelligence platform, not a generic AI SaaS application.

---

# 2. Primary Development Rule

Build the actual product.

Do not build a visual mockup that only looks convincing.

Every UI element that represents system behaviour must have a corresponding implementation path, data model, state, or API contract.

Do not fabricate functionality.

If a capability has not yet been implemented, represent its state honestly rather than pretending it works.

---

# 3. Design Authority

When implementing UI, follow this priority:

1. Explicit task requirements
2. `DESIGN-mastercard.md`
3. `SKILL.md`
4. NEXORA project architecture/context
5. Existing repository architecture
6. Installed component ecosystem
7. General best practices

Do not silently override the design direction established by the project files.

When a design decision is ambiguous, prefer the simplest professional implementation that preserves the established design language.

---

The interface must be:

- Professional
- Clean
- Precise
- Calm
- Modern
- Highly legible
- Visually hierarchical
- Spatially balanced
- Responsive
- Purpose-driven

---

# 6. NO MOCK DATA

Do not introduce hardcoded fake production data merely to make the interface look complete.

Do not invent:

- Energy values
- Occupancy values
- Temperature values
- CO₂ values
- Savings
- Recommendations
- Equipment health
- Sensor states
- Building statistics
- Financial results
- AI confidence values
- Verification results

If data is required for the prototype, it must come from the project's defined:

- simulation engine
- backend
- API
- database
- deterministic test fixture
- or explicitly defined simulation dataset

Clearly separate:

- Real data
- Simulated data
- Assumed data

Never present simulated data as real measured building data.

---

# 7. NEXORA Evidence Discipline

The UI must distinguish between:

### Measured
Data collected from actual building/sensor systems.

### Simulated
Data generated by the NEXORA simulation/prototype environment.

### Assumed
Planning or configuration assumptions.

Never label simulated results as:

- Measured
- Verified
- Real-world savings
- Actual building performance

unless the underlying data genuinely supports that claim.

Use appropriate evidence indicators where required.

- 21st.dev registry
- Magic UI registry
- Aceternity UI-compatible utilities
- Framer Motion

Design quality takes priority over library usage.

For:

- dialogs

- tabs

- tooltips

- command interfaces

- cards
- menus
- navigation
- stateful UI

Use selectively for polished copy-paste components when they genuinely improve the interface.

### Magic UI

- premium motion
- specialised interface elements

Do not turn the entire application into a Magic UI showcase.

### Aceternity UI
Use selectively for sophisticated visual interactions where appropriate.

### Framer Motion
Use for intentional:

- page transitions
- component entrance
- state transitions
- chart transitions
- recommendation state changes
- dashboard interactions

### Lucide
Use as the primary icon system.

### Recharts
Use for:

- energy trends
- actual vs expected
- peak demand

- verification
- historical analysis

Charts must remain readable and technically meaningful.

---

# 10. Animation Philosophy

Animation must communicate system state.

Use animation to show:

- data arriving
- state changing
- recommendations appearing
- actions being approved
- control execution
- verification
- transitions between dashboard states

Avoid animation that exists purely for decoration.

Animation should generally be:

- subtle
- fast
- intentional
- interruptible
- consistent

Never make the interface feel like a game or futuristic demo.

Respect reduced-motion preferences.

---

# 11. Information Hierarchy

The interface should prioritise decisions over raw telemetry.

A facility manager should quickly understand:

1. Is the building healthy?
2. Is energy consumption abnormal?
3. Which zone needs attention?
4. What does NEXORA recommend?
5. Why is it recommending it?
6. Is the action safe?
7. What will happen if the action is executed?
8. Did the action actually work?

Do not overwhelm users with raw sensor values.

Expose detailed telemetry progressively.

# 12. Core NEXORA UI Concepts

The product should visually communicate:

## Building Health

Overall building state.

## Energy

- Current energy
- Expected energy
- Actual vs expected
- Peak demand
- Energy trends
- Anomalies

## Zones

- Occupancy
- Temperature
- CO₂
- Humidity
- HVAC state
- Lighting state
- Zone energy

## AI Recommendations

Each recommendation should communicate:

- What happened
- What NEXORA recommends
- Why
- Expected impact
- Confidence
- Constraints
- Approval state

## Safety Gate

Clearly show:

- Comfort check
- IAQ check
- Equipment check
- Operating-rule check
- Confidence check
- Final decision

The user should understand why an action was allowed or rejected.

## Verification

Show:

BEFORE → ACTION → AFTER → VERIFIED IMPACT

The system should never simply claim that an action worked.

---

# 13. Human-in-the-Loop

NEXORA supports:

### MONITOR
Observe only.

### RECOMMEND
Generate recommendations.

### APPROVE
Require facility-manager approval.

### AUTOMATE
Execute eligible pre-authorised actions.

Manual override must remain easily accessible.

Never hide or bury manual control.

---

# 14. Safety First

NEXORA must never visually imply that AI has unrestricted control over the building.

The conceptual flow is:

AI Recommendation
↓
Digital Twin / What-If
↓
Safety & Constraint Gate
↓
Approval / Automation Policy
↓
Control
↓
Read-back / Acknowledgement
↓
Verification

Safety constraints include:

- Temperature comfort
- CO₂ / IAQ
- Humidity
- Equipment limits
- Operating requirements
- Building criticality
- User overrides
- Model confidence

---

# 15. Responsive Design

The application must work across:

- Desktop
- Laptop
- Tablet
- Mobile where appropriate

The primary facility-manager experience is desktop-first.

Do not simply shrink the desktop UI.

Responsive layouts must preserve:

- hierarchy
- readability
- controls
- charts
- critical status information

---

# 16. Accessibility

Follow accessible web practices.

Ensure:

- sufficient contrast
- keyboard navigation
- visible focus states
- semantic HTML
- accessible labels
- meaningful icon labels
- reduced-motion support
- usable interactive controls

Do not communicate important information through colour alone.

---

# 17. Code Quality

Use:

- TypeScript
- reusable components
- clear naming
- small focused modules
- predictable state management
- existing project utilities
- existing component patterns
